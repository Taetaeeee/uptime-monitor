## 한 줄 소개 (이력서 프로젝트 칸)

> 내가 운영하는 웹 서비스와 팀 채팅을 5분마다 점검해 장애를 감지·기록하고, 가동률과 장애 이력을 공개 상태 페이지와 월간 보고서로 보여 주는 모니터링 도구 (Cloudflare Workers, D1, Python)

## 직무 공통 (기술·성과, 3~4줄)

- Cloudflare Workers 예약 실행과 D1으로 HTTP·DNS 점검, 2회 연속 실패 시 장애 판정, 복구 판정, 알림 기록 체계를 구현했습니다.
- 판정·집계 로직을 순수 함수로 분리하고 JS 212개·Python 22개 테스트를 CI에 연결했습니다.
- 장애 훈련으로 장애 감지(첫 실패 후 5분에 판정) → 복구 → 사후 보고서까지 실제 환경에서 확인했고 기록을 남겼습니다.
- 판정 규칙을 설계에 쓰지 않은 데이터로 측정해, 연속 1회→2회에서 오탐이 약 79% 줄고 탐지율이 40.7%p 떨어지는 교환 관계를 수치로 확인했습니다.

## 직무별 강조

### 인프라 운영
- 장애 감지 시간(MTTD)·복구 시간(MTTR)·가동률·에러 버짓(SLA 99.9%)을 장애 1건 단위로 산출하고, 계획 작업 시간은 가동률에서 제외하는 규칙을 구현했습니다.
- 에이전트가 바깥으로만 연결하는 구조로 설계해 점검 대상 PC의 포트를 열지 않았습니다. 이 구조에서 에이전트가 멈추면 보고가 끊기는 한계를 파악해, "마지막 보고 후 N분 경과"를 실패 점검으로 기록하는 무응답 감지를 만들고 테스트했습니다(대상마다 켜는 방식, 아직 운영에서 켠 대상은 없음).
- 마이그레이션 적용 전 백업, 컷오버 순서 계획, 되돌리기 SQL 준비 등 운영 변경 절차를 지켜 가며 배포했습니다.

### 사내 IT
- 전 직장에서 ERP 운영과 장애 접수·에스컬레이션을 하며 보던 "장애가 났다는 사실을 누가, 언제, 어떻게 아는가"를 도구로 옮겼습니다.
- 장애 1건마다 첫 실패·판정·복구 시각과 사후 보고서 5항목을 남겨, 비개발자에게도 상태 페이지와 PDF 보고서로 설명할 수 있게 했습니다.
- 비밀 값(관리자 토큰·에이전트 키)을 분리하고 저장소에 넣지 않는 방식(wrangler secret, `.dev.vars`)으로 관리했습니다.

### 공공 SM
- 월간 가용성 보고서(대상별 가동률·SLA 달성·장애 지표)를 인쇄/PDF로 저장할 수 있게 만들어, 정기 보고 업무 형태로 구현했습니다.
- 실제 데이터와 가짜 데이터를 출처로 구분해 표시하고, 데이터셋 라이선스를 원본에서 직접 확인해 적는 등 근거 관리를 문서화했습니다.
- 변경마다 계획 → 승인 → 구현 → 확인 명령 → 기록의 단계를 지켰습니다.

## 자기소개서 문단 예시 (400자 안팎)

> 전 직장에서 ERP 운영과 장애 접수를 맡으며, 장애는 "고치는 시간"보다 "알아채는 시간"이 길어질 때 커진다는 것을 겪었습니다. 이를 직접 확인하려고 제가 운영하는 사이트와 팀 채팅을 5분마다 점검하는 모니터링 도구를 만들었습니다. 일시적 흔들림에 알림이 쏟아지지 않도록 2회 연속 실패를 장애로 보았고, 이 선택이 오탐을 약 79% 줄이는 대신 탐지율을 낮춘다는 것을 설계에 쓰지 않은 공개 데이터로 측정했습니다. 다만 그 데이터는 서버 지표라서 제 서비스의 점검 성능을 보장하지 않는다는 점까지 문서에 적었습니다. 실제 장애 훈련으로 감지부터 복구, 사후 보고서까지 확인했고, 실제 점검과 재생 데이터를 출처로 구분해 보여 줍니다. 이런 식으로 확인되지 않은 것은 확인되지 않았다고 말하며 운영하겠습니다.

## 쓰지 말아야 할 표현
- "실시간 모니터링 서비스를 운영 중" — 점검 대상은 내 사이트와 Keychats 둘이고, 나머지 서비스는 재생 데이터입니다.
- "장애를 N% 탐지" — 44.7%는 서버 지표 공개 데이터의 값이지 이 서비스의 HTTP 점검 성능이 아닙니다.
- "수십 대 서버 점검" — 내부 점검은 시뮬레이터와 훈련용 포트 1개입니다.
- "프로덕션 규모" — D1 무료 한도 안의 소규모입니다.
